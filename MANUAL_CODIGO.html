3. Patrones de diseno

3.1 Factory Method

Archivo: factory/PrendaFactory.java

Problema: El sistema necesita crear tres tipos de prenda (vestido, traje, disfraz) con atributos distintos. Sin el factory, el codigo cliente tendria que conocer y decidir que clase concreta instanciar.

Como funciona: PrendaFactory.crearPrenda() recibe un TipoPrenda y delega la creacion a la clase concreta correspondiente. El resto del sistema trabaja con la abstraccion Prenda y no conoce las clases concretas.

PrendaFactory.crearPrenda(VESTIDO, ...)
  └── new Vestido(...)
PrendaFactory.crearPrenda(TRAJE, ...)
  └── new Traje(...)
PrendaFactory.crearPrenda(DISFRAZ, ...)
  └── new Disfraz(...)

Donde se usa: FacadeAlquiler.registrarPrenda() llama al factory para crear la prenda antes de persistirla. El panel PanelPrendas no sabe que clase concreta se instancia.

3.2 Builder

Archivo: builder/ServicioAlquilerBuilder.java

Problema: Un ServicioAlquiler tiene muchos atributos obligatorios (fechas, cliente, empleado, lista de prendas, precio). Construirlo en una sola llamada seria confuso y propenso a errores.

Como funciona: El builder expone metodos fluentes (conCliente(), conFechaAlquiler(), agregarPrenda(), etc.) que acumulan los datos. Al llamar construir(numeroConsecutivo), valida que todos los obligatorios esten presentes y crea el ServicioAlquiler con el composite de prendas ya armado.

ServicioAlquilerBuilder builder = new ServicioAlquilerBuilder()
    .conCliente(cliente)
    .conEmpleado(empleado)
    .conFechaAlquiler("2025-11-01")
    .conFechaDevolucion("2025-11-05")
    .agregarPrenda(prenda1)
    .agregarPrenda(prenda2)
    .conPrecioTotal(50000);

ServicioAlquiler servicio = builder.construir(1);

Donde se usa: FacadeAlquiler.crearServicioAlquiler() actua como director: carga y valida cliente, empleado y prendas, los pasa al builder y le inyecta el numero consecutivo.

3.3 Facade

Archivo: facade/FacadeAlquiler.java

Problema: La interfaz grafica necesitaria interactuar con cinco repositorios, un factory, un builder y un decorator para realizar las operaciones del negocio. La fachada oculta toda esa complejidad.

Como funciona: FacadeAlquiler expone metodos simples. Internamente coordina los repositorios y patrones correspondientes. Todos los paneles GUI reciben la misma instancia de la fachada.

Operacion Metodo

Listar clientes listarClientes()
Registrar empleado registrarEmpleado(Empleado e)
Listar empleados listarEmpleados()
Registrar prenda (Factory) registrarPrenda(TipoPrenda, ...)

3.4 Composite

Archivos: composite/ComponenteAlquiler.java, composite/PrendaIndividual.java, composite/ConjuntoPrendas.java

Problema: Un servicio de alquiler puede contener una o varias prendas. El sistema necesita tratarlas de forma uniforme, sin diferenciar si es una sola prenda o un conjunto.

Como funciona: ComponenteAlquiler es la interfaz comun. PrendaIndividual envuelve una prenda (hoja). ConjuntoPrendas contiene varios componentes (compuesto). Ambos implementan getPrendas(), disponiblePara(fecha) y resumen().

ComponenteAlquiler
├── PrendaIndividual  → una prenda
└── ConjuntoPrendas   → varias PrendaIndividual

Donde se usa: El ServicioAlquilerBuilder arma el composite al construir el servicio. Si hay una prenda, crea PrendaIndividual. Si hay varias, crea ConjuntoPrendas y agrega cada una. ServicioAlquiler.getListaPrendas() delega al composite para obtener la lista plana.

3.5 Decorator

Archivos: decorator/Priorizable.java, decorator/PrioridadPrenda.java, decorator/PrioridadDecorator.java

Problema: Las prendas devueltas van a lavanderia. Algunas necesitan prioridad especial sin modificar la clase original Prenda.

Como funciona: PrioridadPrenda envuelve una Prenda y le asigna prioridad NORMAL por defecto (nivel 1). PrioridadDecorator envuelve una Priorizable y eleva su prioridad a PRIORITARIA (nivel base + 10). La prenda original no se modifica.

Prenda → PrioridadPrenda (nivel 1, NORMAL)
       └── PrioridadDecorator (nivel 11, PRIORITARIA)

Donde se usa: FacadeAlquiler.listarPendientesLavanderia() recupera las prendas pendientes, envuelve las prioritarias con PrioridadDecorator y las ordena por nivel descendente. El panel de lavanderia muestra el nivel en la tabla.

3.6 Adapter

Archivos: persistencia/RepositorioPrendas.java (interfaz), persistencia/RepositorioPrendasH2.java (adaptador)

Problema: La logica del negocio no debe depender de una tecnologia de persistencia concreta. Si se cambia de H2 a MySQL, no se debe modificar la fachada ni los modelos.

Como funciona: RepositorioPrendas define el contrato (guardar, buscarPorId, listarTodas, disponiblePara). RepositorioPrendasH2 implementa esa interfaz traduciendo las operaciones a SQL sobre H2. La fachada usa la interfaz, no la implementacion concreta.

RepositorioPrendas (interfaz del negocio)
    ↑ implementa
RepositorioPrendasH2 (adapta a SQL/H2)

Como cambiar de base de datos: Crear una nueva clase que implemente RepositorioPrendas (por ejemplo RepositorioPrendasMySQL) y cambiar la instancia en la fachada. El resto del sistema no se modifica.

4. Base de datos

Motor: H2 embebida (archivo losatuendos.mv.db)
Conexion: ConexionBD.obtener() devuelve una Connection JDBC

Esquema relacional

Creacion automatica

EsquemaBD.crearSiNoExiste() ejecuta todos los CREATE TABLE IF NOT EXISTS al arrancar la aplicacion. No requiere scripts manuales.

Disponibilidad de prendas

La consulta disponiblePara(idPrenda, fecha) verifica dos condiciones:

  1. La columna disponible de la prenda sea TRUE
  2. No exista un servicio ACTIVO que incluya esa prenda y cuya fecha solicitada este entre fecha_alquiler y fecha_devolucion

6. Flujo de una operacion completa

Ejemplo: crear un servicio de alquiler con dos prendas.

1. Usuario completa formulario en PanelServicios
2. PanelServicios llama a facade.crearServicioAlquiler(idCliente, idEmpleado,
   idsPrendas, fechaAlquiler, fechaDevolucion, precio)
3. FacadeAlquiler:
   a. Busca el cliente en RepositorioClientes (valida que exista)
   b. Busca el empleado en RepositorioEmpleados (valida que exista)
   c. Por cada prenda: busca en RepositorioPrendasH2 (Adapter)
      y verifica disponibilidad con disponiblePara(id, fecha)
   d. Pasa todo al ServicioAlquilerBuilder (Builder)
   e. Builder.construir() valida campos obligatorios
      y arma el ComponenteAlquiler (Composite)
   f. RepositorioServicios.siguienteConsecutivo() obtiene el numero
   g. RepositorioServicios.guardar() persiste encabezado + relaciones
   h. Marca las prendas como no disponibles
4. PanelServicios muestra mensaje de confirmacion y recarga la tabla

7. Manejo de errores

  • Las validaciones de campos lanzan IllegalArgumentException con el mensaje especifico, que se muestra en un dialogo de error
  • Los errores de base de datos lanzan SQLException que se capturan en los paneles y se muestran al usuario
  • El builder lanza IllegalStateException si faltan datos obligatorios
  • No se permite registrar duplicados (documento de cliente/empleado, codigo de prenda)

8. Decisiones de diseno documentadas

Decision Justificacion
H2 embebida en vez de MySQL/PostgreSQL No requiere instalar un servidor. El patron Adapter permite cambiar a otra BD creando un nuevo adaptador que implemente RepositorioPrendas.
Interfaz de escritorio Swing Cumple el requisito de interfaz grafica sin anadir dependencias externas.
Java 11 El sistema tiene Java 11 instalado. El pom original usaba Java 18 pero no podia ejecutarse.
Contador en BD El numero consecutivo se lleva con una tabla contador_alquiler que se incrementa de forma atomica.
Capacidad de tanda configurable El documento no especificaba cuantas prendas caben por tanda. Se deja a criterio del usuario en el momento de organizar.
Logo cargado desde archivo El logo se lee desde src/main/ en tiempo de ejecucion. Si no se encuentra, se omite sin error.
